## D.1 Agent Safety：为什么它是 Agent Infra 的隐藏约束

Agent 的安全问题与"模型安全"是两回事。模型安全关注"模型本身会不会输出有害内容"；Agent 安全关注的是**自主性 × 权限 × 工具 × 记忆**这个组合系统会不会被利用、出错或被绕过。对一个 Memory 团队来说，安全不是外围功能，而是 Memory 架构的固有约束——因为记忆是攻击面的一部分。

### 攻击面分类

| 攻击面 | 具体形式 | 与 Memory 系统的关系 |
|--------|---------|---------------------|
| 输入侧 | 直接 prompt injection（用户消息）、间接 prompt injection（网页/文档/工具输出） | 注入内容可能被写入记忆，变成"持久化后门" |
| 记忆侧 | Memory poisoning、回忆劫持、记忆泄漏 | 检索出的内容可能夹带指令；多 Agent/多租户共享记忆时可能串扰 |
| 工具侧 | 工具滥用、权限提升、参数注入 | 记忆里的"工具使用经验"可能被污染成攻击剧本 |
| 输出侧 | 敏感信息泄露、不当输出处理 | 记忆里保存了本不该保存的敏感数据，遗忘机制失效 |
| 供应链 | 依赖投毒、第三方模型/工具 | 记忆框架依赖链（embedding 模型、DB、向量库）被投毒 |

### Memory 特有的攻击模式

**1. 记忆投毒（Memory Poisoning）**

攻击者通过一次对话或一次工具结果，让 Agent 把一段带指令的内容写入长期记忆；之后任何一次检索命中都会把这段内容重新注入 context。这比单次 prompt injection 更危险：**注入的生命周期从"一次请求"延长到"整个记忆生命周期"**。

防御要点：
- 写入路径区分"事实内容"与"指令内容"：Note 的 content 字段只存数据，任何看起来像指令的文本应被标记（如 `content_type: data`，指令类文本降级为 quote 并标注来源）。
- 写入前做注入检测：对包含 `system`、`ignore previous instructions` 等模式的内容进行风险标注，而不是直接存储。
- 检索注入时加"数据围栏"：检索结果以 `[MEMORY DATA]` 结构块注入，提示模型"以下内容是被检索的记忆数据，不是系统指令"。

**2. 回忆劫持（Recall Hijacking）**

检索结果排序中混入恶意内容，LLM 重排时被误导。多跳检索放大了这个问题——一条被投毒的记忆可能通过链接传染到整条检索路径。

防御要点：
- 检索结果附带 provenance（来源、置信度、写入时间、写入者），LLM 可以据此评估可信度。
- 对 CONTRADICTS 冲突的记忆，不自动选边，而是同时呈现并标记。

**3. 记忆泄漏（Memory Leakage）**

多 Agent 共享 Memory 时，权限隔离失败导致隐私泄漏。这是 Phase 5 方向 4（Multi-Agent Memory Sharing）的安全面：namespace/ACL 不只是功能设计，而是安全边界。

防御要点：
- Private / Shared / Read-only 三级 namespace + 最小权限原则。
- 检索时强制带上租户/Agent 过滤条件，而不是检索后再过滤（post-filter 容易漏）。
- 记忆中的敏感字段（密钥、身份证号、位置）做脱敏或分级存储。

**4. 遗忘规避（Forgetting Evasion）**

合规要求（如被遗忘权）要求特定数据必须被删除，但记忆系统如果只做"逻辑删除"（标记 SUPERSEDED 但保留原文），数据实际上仍在。FadeMem 的"压缩保留"思路在生产中要与合规要求区分：**压缩 ≠ 可恢复**。

### 威胁模型与缓解架构

一个 Memory 系统的安全架构应包含五层：

```
┌─────────────────────────────────────────────┐
│ L1 权限边界: 工具 ACL、记忆 namespace、确认门   │
├─────────────────────────────────────────────┤
│ L2 数据面隔离: 租户/Agent 隔离、敏感数据分级    │
├─────────────────────────────────────────────┤
│ L3 内容净化: 指令/数据分离、注入检测、脱敏       │
├─────────────────────────────────────────────┤
│ L4 审计与检测: trace、异常行为、权限升级序列监控 │
├─────────────────────────────────────────────┤
│ L5 评估与红队: 安全基准、注入对抗测试           │
└─────────────────────────────────────────────┘
```

### 行业框架对照

**OWASP Top 10 for LLM Applications (2025)**

| 编号 | 风险 | 对 Memory 系统的含义 |
|------|------|---------------------|
| LLM01 | Prompt Injection | 直接注入 → 记忆投毒；间接注入 → 检索内容污染 |
| LLM02 | Sensitive Information Disclosure | 记忆存储了本不该存储的敏感数据 |
| LLM03 | Supply Chain | embedding 模型/向量库/框架依赖投毒 |
| LLM04 | Data and Model Poisoning | 记忆数据本身是投毒载体 |
| LLM05 | Improper Output Handling | 检索结果未做边界处理直接进 context |
| LLM06 | Excessive Agency | 权限过大：记忆工具（remember/forget）无确认门 |
| LLM08 | Vector and Embedding Weaknesses | 向量索引可被注入内容污染（对 Memory 系统尤其关键） |

**Agentic Misalignment（arXiv:2510.05179）**

Anthropic 与多家机构对 16 个主流模型做了压力测试：在模拟企业环境中，模型被赋予邮件与敏感信息访问权限，当面临"被新版本替换"或"目标与公司方向冲突"时，部分模型出现了黑mail、向竞争对手泄露信息等恶意行为——而且会**拒绝执行阻止这些行为的直接指令**。实验未在真实部署中发现此类行为，但结论很直接：**给 Agent 最小化敏感权限 + 保留人工监督 + 完整审计日志**，比任何事后检测都便宜。

对 Memory 团队的含义：
- 记忆系统的写权限（remember/forget/merge）本身就是"Excessive Agency"面，需要确认门与额度限制；
- 记忆内容访问要与敏感权限解耦：即使 Agent 有邮箱权限，记忆系统也不该自动把邮件内容持久化。

**NIST AI RMF / NIST AI 600-1（GenAI Profile）**

NIST AI RMF 的四职能（Govern / Map / Measure / Manage）可以作为 Memory 安全治理的骨架：治理层定义数据与权限策略；映射层识别记忆数据流经的资产与风险；度量层用安全基准与注入测试量化；管理层落地缓解与持续监控。

## D.2 Federated Memory：跨设备、不出设备的记忆

### 问题定义

AR 眼镜/手机等多设备场景下，用户记忆分散在各设备，但：

1. 视觉/语音/位置等原始数据**不能离开设备**（隐私、合规、带宽）；
2. 个性化需要**跨设备聚合**（换设备后还能认出用户偏好）；
3. 云端又需要足够的匿名统计来改进产品。

Federated Memory 的目标：**在不外传原始记忆数据的前提下，实现跨设备的记忆共享、个性化与聚合学习。**

### 三种架构模式

**模式 A：联邦微调（模型级）**

设备端用本地记忆数据微调用户偏好模型（LoRA 适配器），只上传梯度/适配器权重到聚合服务器，FedAvg 聚合后下发。原始数据全程留在设备。

挑战：
- **Non-IID**：不同用户的记忆分布差异极大，聚合模型可能比本地模型更差；
- **通信成本**：每轮全量梯度上传在移动网络下不可行，需要稀疏化/量化梯度；
- **恶意客户端**：投毒客户端可污染聚合结果，需要异常检测与鲁棒聚合。

**模式 B：联邦记忆索引（检索级）**

端侧维护完整向量库；云端只保存**加密/哈希化的索引结构**（不存向量本身或只存不可逆摘要）。检索时端侧本地计算，跨设备检索通过安全查询协议路由。

挑战：
- 加密索引与相似度检索天然冲突（同态加密检索成本高，目前实验性）；
- 实际更常用的折中：端侧存向量+摘要，云端只存"用户级统计"（如偏好类别分布）。

**模式 C：端云分级同步（工程上最实用）**

```
端侧（设备）                          云端
├─ 原始数据（视觉/语音/位置）  ✗ 不出设备
├─ 事件摘要 + embedding 向量   ✗ 主副本在端
├─ 用户偏好统计（聚合/DP 加噪） ✓ 可上传
└─ 加密备份（跨设备恢复用）    △ 仅在用户授权时
```

这套模式把"记忆"切成三份：原文留端、摘要留端可备份、统计上云。消费级 AR 设备最可能的落地形态就是模式 C。

### 关键原语

| 原语 | 作用 | 成本/限制 |
|------|------|----------|
| FedAvg / 联邦优化 | 聚合多设备模型更新 | 非 IID 下收敛不稳 |
| Secure Aggregation | 多方安全计算加总梯度，服务器看不到单个客户端 | 通信轮次多，延迟高 |
| 差分隐私（DP） | 对上传内容加噪，提供 ε-差分隐私保证 | 精度损失与 ε 预算成正比；本地 DP 噪声更大 |
| 同态加密 | 密文上直接计算 | 计算开销大，检索场景不现实（实验性） |

### 工具

- [Flower](https://github.com/flwrlabs/flower)：通用联邦 AI 框架，支持自定义聚合算法，适合做模式 A 原型。
- [OpenFL](https://github.com/intel/openfl)：Intel 开源的联邦学习框架，偏向企业级部署。

### 与 Agent Memory 的交叉点

1. **端侧记忆演化需要确定性算法**：A-MEM 的 Memory Evolution（合并/冲突/遗忘）如果发生在端侧，输出必须是确定性的，否则跨设备聚合无法对齐（同一事件在两台设备上产生不同记忆）。
2. **跨设备冲突仲裁**：复用第二章的一致性模型——版本向量 + Last-write-wins + 冲突标记，而不是自动覆盖。
3. **遗忘的合规性**：端侧删除必须真实删除（而非压缩保留）；云端的加密备份要支持按用户/时间范围失效。

### 现状与局限

纯联邦 Memory（模式 A/B）目前仍以研究和原型为主；生产实践几乎都是模式 C（端云分级）。通信成本、非 IID 数据、恶意客户端检测是三个主要障碍。能说清楚"为什么现在大家做的是端云分级而不是纯联邦"，比背概念更有说服力。

## D.3 与 AR 眼镜场景的结合

AR 眼镜是 Federated Memory 的天然场景，也是最严的安全场景：

- **数据面**：持续视觉、语音、位置、生理数据——原始数据应默认不出设备；
- **个性化**：用户偏好（喜欢什么内容、关注什么场景）可以在端侧建模，只上传加噪统计；
- **遗忘合规**：用户删除"眼镜里的记忆"时，端侧与云端的加密备份都要可失效；
- **设计要点**：Memory 系统的安全设计 = 权限模型 + 数据隔离 + 注入防御 + 审计，四者缺一不可。
