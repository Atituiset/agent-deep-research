## E.1 多模态 Memory 的问题定义

AR 眼镜的输入远不止文本：视频帧、语音、空间位置、手势、IMU 数据都在产生"记忆素材"。多模态 Memory 要回答三个问题：

1. **记什么**：视觉事件（"上周四这家咖啡店"）、语音对话、空间关系（"厨房在客厅左边"）、语义偏好（"喜欢安静的环境"）——不同模态的信息密度和检索方式完全不同。
2. **怎么组织**：是每种模态独立索引，还是统一到一个跨模态语义空间？
3. **怎么检索**：用文本 query 检索图片记忆、用图片 query 检索文本记忆——需要跨模态对齐。

### 记忆条目的模态类型

| 类型 | 输入 | 存储形式 | 检索方式 |
|------|------|---------|---------|
| 视觉记忆 | 视频帧/照片 | 视觉特征向量 + 场景描述 | 图搜图 / 文本搜图 |
| 语音记忆 | 音频流 | ASR 文本 + 说话人 + 音频特征 | 文本检索 + 说话人过滤 |
| 空间记忆 | 位置/场景图 | 坐标 + 场景图节点 | 位置邻近 + 实体链接 |
| 事件记忆 | 多模态混合 | 时间线事件 + 各模态摘要 | 时间 + 实体 + 语义 |
| 语义记忆 | 文本/对话 | Note（沿用 A-MEM 结构） | 向量 + 图谱 |

## E.2 多模态编码与统一索引

### 编码层选型（端侧可跑）

| 模态 | 模型 | 规模 | 端侧可行性 |
|------|------|------|-----------|
| 文本 | all-MiniLM-L6-v2 | 22M 参数 / 384 维 / fp32 约 90MB（int8 约 25MB） | ✅ 常驻，单条 5–20ms |
| 文本（中文） | bge-small-zh-v1.5 | 24M 参数 / 512 维 | ✅ |
| 视觉 | MobileCLIP-S2 | 约 15M 参数 | ✅ 帧级 10–50ms（NPU） |
| 视觉（更强） | CLIP ViT-B/32 | 约 150M 参数（图像编码器约 87M） | △ int8 约 250MB，看预算 |
| 语音 | Whisper tiny | 39M 参数 | ✅ 短句 100–300ms |

### 统一索引策略

推荐"**分模态索引 + 元数据联合过滤 + 跨模态重排**"三层结构，而不是把所有模态塞进一个向量空间：

```
┌──────────────────────────────────────────────────┐
│ 结构化元数据（SQLite）                            │
│ 类型 | 时间 | 位置 | 实体 | 说话人 | 置信度        │
├──────────────────────────────────────────────────┤
│ 模态向量库（sqlite-vec / 端侧 FAISS）             │
│ 文本向量(384d) + 视觉向量(512d) + 音频向量(384d)  │
├──────────────────────────────────────────────────┤
│ 跨模态对齐层（可选）                              │
│ CLIP 式图文对齐：视觉与文本特征映射到同一空间       │
└──────────────────────────────────────────────────┘
```

检索时：
1. **硬过滤**：用 SQL 先按 类型/时间/位置/实体 过滤（post-filter 会漏，先过滤再向量搜索）；
2. **模态向量检索**：文本 query 的 embedding 同时检索文本库和视觉库（经跨模态映射）；
3. **融合重排**：对候选做 LLM 或轻量交叉编码器重排，合并相似项；
4. **provenance 注入**：每条记忆带来源与置信度，供 LLM 评估。

### 一个具体例子

"上周四在咖啡店见过的那个人"：

```
query 解析:
  时间: 上周四 → 元数据过滤 [last_week_thursday]
  位置: 咖啡店 → 位置过滤 + POI 实体链接
  人物: 那个人 → 视觉特征 + 人脸 embedding（若有人脸识别）

检索计划:
  SQL: type=visual AND time BETWEEN ... AND location_near(cafe)
  → 候选视频帧/照片
  视觉向量相似度 top-k → 去重（同一场景多帧合并）
  → 文本摘要（"和 X 一起喝咖啡"）→ 语义重排
```

这个例子说明多模态 Memory 的核心工程点：**元数据过滤比向量检索更先发挥作用**——纯向量检索解决不了时间/位置这类精确约束。

## E.3 端侧约束模型（示例数据）

### 设备假设

以消费级 AR 眼镜 + 手机端处理器为参考：

| 资源 | 假设预算 | 说明 |
|------|---------|------|
| RAM（AI 可用） | 300–500 MB | 与系统/渲染进程共享 |
| Flash（AI 数据） | 10–20 GB | 模型 + 长期记忆 |
| 推理后端 | TFLite / ONNX Runtime / llama.cpp | NPU 优先，CPU 兜底 |
| 实时检索延迟 | <500 ms | "看着一个东西"场景 |

### 模型内存预算

| 模型 | 大小 | 驻留策略 |
|------|------|---------|
| all-MiniLM-L6-v2（int8） | ~25 MB | 常驻 |
| MobileCLIP-S2（int8） | ~20–40 MB | 常驻 |
| Whisper tiny（int8） | ~40 MB | 按需加载 |
| Llama-3.2-1B（int8） | ~1.2 GB | ⚠️ 超出常驻预算 → 后台任务按需加载，或退到 0.5B 级 |

结论：**embedding + 视觉特征模型可以常驻（<100 MB），小 LLM 只能在后台任务按需加载**。这也是为什么端侧记忆的"写入/演化"要用小模型异步做，而"检索"只用 embedding。

### 存储预算测算（6 个月使用）

假设每天 150 条记忆事件：

```
180 天 × 150 = 27,000 条

每条成本:
  文本摘要    ~150 tokens → 压缩后 ~0.15 KB
  文本向量    384d fp16  → 0.75 KB
  视觉特征    512d fp16  → 1.0 KB（含缩略图则 +5–20 KB）
  元数据      ~0.3 KB

总量（不含缩略图）:
  27,000 × (0.15 + 0.75 + 1.0 + 0.3) KB ≈ 60 MB
  加上索引与 SQLite 开销 ≈ 80–120 MB
```

结论：**容量不是瓶颈**（远低于 10 GB 预算），瓶颈在检索延迟与写入成本。这也是端侧 Memory 与云端 Memory 的最大差异——云端系统常为容量优化，端侧系统为延迟/功耗优化。

### 延迟预算分解

实时检索路径：

| 步骤 | 预算 |
|------|------|
| 图像/语音 → 事件提取（端侧小模型） | 150–300 ms |
| 文本 embedding | 10–20 ms |
| SQLite + sqlite-vec 检索（先过滤后向量） | 10–50 ms |
| 小 LLM 重排/摘要 | 100–250 ms |
| 注入 context | ~0 ms |
| **合计** | **270–620 ms** |

优化手段：
1. **去掉 LLM 重排**：检索后直接 top-k 注入，省 100–250 ms；
2. **缓存高频记忆**：常问实体（家人、常去地点）做结果缓存；
3. **预计算摘要**：事件写入时异步生成摘要，检索时不现场调用 LLM；
4. **NPU 并行**：特征提取与文本 embedding 流水线化。

更稳的设计：**80% 请求走端侧快速路径（<500 ms），复杂查询走云端（<1.5 s 体验降级）**。

### 端云分级

| 数据 | 位置 | 理由 |
|------|------|------|
| 视觉/语音/位置原始数据 | 端侧（不出设备） | 隐私 + 带宽 |
| 事件摘要 + 向量 | 端侧主副本，云端仅加密备份 | 跨设备恢复 |
| 用户偏好聚合统计 | 云端（联邦聚合/DP 加噪） | 个性化与产品改进 |

## E.4 量化与推理优化技术

### 量化路径

```
FP32 → FP16 → INT8（PTQ 或 QAT）→ INT4

检索类任务（embedding/特征）:
  INT8 通常可接受（检索质量损失 <1–2%，与维度、数据分布有关）
  建议 PTQ + 少量校准集，逐层看精度曲线

生成类任务（小 LLM）:
  INT8 质量尚可；INT4 需要 QAT 或高质量量化方案（如 GPTQ/AWQ）
  摘要这类"容错"任务可承受更多压缩，冲突检测这类任务要保守
```

### 部署工程点

1. **算子兼容性**：NPU 对 GELU/SiLU、attention、动态 shape 支持差异大，先跑算子清单再选模型；
2. **内存驻留 vs 加载**：模型加载 1–3 秒是端侧体验杀手，常驻模型总预算必须提前规划；
3. **电量预算**：NPU 推理比 CPU 省 5–10 倍功耗，但持续视觉编码仍是耗电大户——用事件触发而非连续编码；
4. **模型蒸馏替代**：MobileCLIP、MiniLM 系列本身就是蒸馏产物，优先选"为端侧设计的模型"，而不是把大模型压小。

### 与 Memory 的结合

- embedding 模型常驻（检索关键路径）；
- 小 LLM 后台任务（Note 构建、链接判断、摘要）按需加载，串行执行，避免内存峰值；
- 云端大模型只处理复杂任务（跨模态重排、冲突仲裁、全局遗忘策略），且结果以"摘要/决策"形式回写端侧，不回传原始数据。
